# 绿立方农批交易小程序平台 - 设计文档

> 日期：2026-07-25
> 版本：v1.0 (MVP)

---

## 1. 项目概述

### 1.1 项目背景
绿立方是一个面向农产品批发市场的线上交易小程序平台，连接买家（餐厅、生鲜店、单位食堂等）、供应商（农批商户、产地合作社）和送货司机三方，实现农产品的在线交易与同城配送。

### 1.2 MVP 核心目标
跑通完整交易闭环：**买家下单 → 供应商接单 → 司机配送 → 收货确认 → 平台结算**

### 1.3 范围与边界
- **运营范围**：单城市/区域起步，后续可扩张
- **支持平台**：微信小程序（买家/供应商/司机三端合一） + 运营管理 H5 后台
- **本期不做**：多城市切换、跨城配送、竞拍模式、账期结算、App 端

## 2. 核心决策汇总

| # | 决策项 | 结论 |
|---|--------|------|
| 1 | MVP核心 | 交易闭环（下单→接单→配送→确认→结算） |
| 2 | 配送模式 | 自动派单 + 抢单池，支持供应商自有司机 |
| 3 | 交易模式 | 标准电商模式（供应商发布商品，买家直接下单） |
| 4 | 结算方式 | 平台托管结算（买家付款到平台商户号 → 确认收货后平台转账给供应商） |
| 5 | 覆盖范围 | 单城市/区域起步 |
| 6 | 产品形态 | 单微信小程序多角色切换 + 运营管理 H5 后台 |
| 7 | 商品品类 | 全品类覆盖，不同品类有不同规格属性模板 |
| 8 | 用户认证 | 买家宽松注册（手机号），供应商/司机需平台审核入驻 |
| 9 | 运费计价 | 固定运费 + 阶梯价（满额可免运费） |

| 14 | 后端技术栈 | Node.js (NestJS + TypeScript) |

## 3. 角色与权限

### 3.1 三大角色

| 角色 | 典型用户 | 核心诉求 |
|------|---------|---------|
| 🛒 买家 | 餐厅采购、生鲜店老板、单位食堂负责人 | 找货方便、价格透明、送货及时、质量可靠 |
| 🏪 供应商 | 农批市场商户、产地合作社、农产品批发商 | 扩大销路、订单管理、高效配送、资金安全 |
| 🚚 司机 | 平台注册司机、供应商自有司机 | 订单充足、路线合理、结算及时 |

### 3.2 角色切换设计
- 一个用户账号可以同时拥有多个角色（例如：既是买家又是供应商）
- 小程序内通过「我的」页面的角色切换入口进行切换
- 不同角色看到的首页和 Tab 栏不同

### 3.3 入驻审核
- **买家**：手机号注册即可使用，下单/支付时触发微信实名
- **供应商**：提交申请 → 上传营业执照 + 食品经营许可证 → 平台审核 → 审核通过后可发布商品
- **司机**：提交申请 → 上传驾驶证 + 行驶证 + 车辆信息 → 平台审核 → 审核通过后可接单

### 5.4 支付与结算模块

**MVP 支付方案说明：**
不走微信支付分账 API（开通门槛高，需特约商户+场景审核+30%比例上限），采用更可控的「平台托管结算」方案：
1. 买家通过微信 JSAPI 支付，款项进入**平台普通商户号**
2. 系统为每个供应商和司机建立**内部资金账户**（余额台账）
3. 订单确认收货后，平台扣除佣金，将剩余款项**记入供应商和司机的内部账户余额**
4. 供应商/司机发起提现时，平台通过**微信商户转账到零钱/银行卡**接口打款
5. 所有资金变动均写入财务流水，确保每笔资金可追溯

**功能范围：**
- 微信支付：小程序内 JSAPI 支付、支付回调、支付结果查询
- 内部账户：为每个供应商/司机建立资金余额台账
- 佣金计算：按订单商品金额 × 佣金比例（可配置，不同品类可不同）
- 运费分配：买家支付的运费按比例分配给司机（MVP 默认 100% 给司机，平台不抽运费佣金，后续可调整）
- 自动结算：确认收货后 T+1 自动将款项（扣除佣金后）划入供应商/司机的内部账户
- 提现管理：供应商/司机发起提现申请 → 平台审核（MVP 可自动审核）→ 商户转账到零钱/银行卡 → 提现记录
- 财务流水：所有资金变动明细（收入/支出/冻结/解冻/提现/退款），每笔关联订单号或业务单号

**结算周期（MVP）：**
- 供应商：确认收货后 T+1 自动结算到内部账户，可随时提现（最低提现额 100 元）
- 司机：确认收货后 T+1 自动结算到内部账户，可随时提现（最低提现额 50 元）
- 平台收入：订单佣金在结算时直接扣除，进入平台收入账户

**核心数据：**
- Payment: id, orderId, userId, amount, payMethod(wechat), payStatus, transactionId, paidAt, callbackData
- UserAccount: id, userId, role(supplier/driver), balance(可用余额), frozenBalance(冻结余额), totalIncome(累计收入), updatedAt
- Settlement: id, orderId, supplierId, supplierAmount, driverId, driverAmount, commissionFee, settleStatus, settledAt
- Withdraw: id, userId, role(supplier/driver), amount, fee(手续费), actualAmount, payMethod(wechat_transfer/bank), bankAccount, auditStatus, auditRemark, transactionId, paidAt, createdAt
- FinanceFlow: id, userId, accountId, type(income/expense/freeze/unfreeze/withdraw/refund), amount, balanceAfter, relatedOrderNo, relatedType, remark, createdAt

### 5.5 配送模块

**功能范围：**
- 运费计算：基础运费 + 超出距离阶梯加价 + 满额免运费 + 不同时效不同价（可配置）
- 自动派单：供应商接单后，根据司机位置、车辆类型、评分、当前负载等自动派单
- 抢单池：自动派单超时无人接的订单进入抢单池，附近司机可见并抢单
- 自有司机：供应商可管理自己的司机，接单后直接指派，不走平台派单
- 配送跟踪：司机位置实时上报、买家查看司机实时位置和预计到达时间
- 配送状态：待取货 → 已取货 → 配送中 → 已送达 → 已签收

**配送跟踪技术实现（MVP）：**
- **司机端定位上报**：使用微信小程序 `wx.startLocationUpdateBackground` + `wx.onLocationChange` 开启后台持续定位（需用户授权），每 15-30 秒上报一次位置到后端（HTTP POST），同时检测到位置变化超过 50 米时主动上报
- **后端位置存储**：Redis 中存储司机最新位置（key: `driver:location:{driverId}`，包含 lat/lng/timestamp），MySQL 存储历史轨迹用于后续分析
- **买家端实时位置**：买家端通过 **WebSocket（Socket.IO）** 建立长连接，订阅当前订单的司机位置更新；后端收到司机位置上报后，通过 WebSocket 推送给对应买家
- **地图渲染**：使用腾讯地图小程序 SDK（`qqmap-wx-jssdk`）渲染司机位置标记、配送路线、预计到达时间（ETA）
- **备选降级方案**：若 WebSocket 不稳定，买家端每 10 秒轮询一次司机位置接口作为降级

**派单算法（MVP简化版）：**
1. 获取取货地址周围 5km 内、状态为「空闲」的司机
2. 按距离从近到远排序，同时考虑司机评分（评分低的降权）
3. 推送给前 3 名司机，每人有 30 秒响应时间
4. 无人接单则推送给下一批，直至进入抢单池

**核心数据：**
- Delivery: id, orderId, driverId, deliveryType(platform/owned), pickupAddress, deliveryAddress, distance, deliveryFee, status, driverLocation(lat,lng,updatedAt), expectedArrivalTime, acceptedAt, pickedAt, deliveredAt, signedAt, createdAt
- DeliveryConfig: id, city, baseFee, baseDistance, perKmFee, freeDeliveryThreshold, sameDayFeeExtra, nextDayFeeExtra, timeSlotFee[]
- DriverStatus: driverId, status(idle/busy/offline), currentDeliveryId, location(lat,lng,updatedAt)

### 5.6 售后模块

**功能范围：**
- 售后申请：买家在已完成订单7天内可发起，选择类型（退款/退货退款/换货）、填写原因、上传凭证图片

- 平台仲裁：双方协商不成，买家可申请平台介入，运营查看双方举证后裁决
- 退款处理：根据裁决结果执行退款（全额/部分）

**核心数据：**
- AfterSale: id, orderId, buyerId, supplierId, type(refund/return/exchange), reason, description, images[], status, buyerAmount, supplierAmount, platformDecision, decisionRemark, appliedAt, supplierProcessedAt, arbitratedAt, closedAt
- AfterSaleMsg: id, afterSaleId, senderId, senderRole, content, images[], createdAt

### 5.7 消息通知模块

**微信订阅消息说明：**
微信已废弃「模板消息」接口，当前使用「一次性订阅消息」——每次推送需要用户在小程序内主动点击授权订阅，一次订阅对应一次推送。因此需要在业务流程的关键节点引导用户订阅。

**需引导订阅的关键节点：**
- 买家下单成功后：引导订阅「订单状态通知」「配送进度通知」
- 供应商入驻审核通过后：引导订阅「新订单通知」「结算到账通知」
- 司机入驻审核通过后：引导订阅「新派单通知」「结算到账通知」
- 首次进入消息中心时：引导订阅所有相关模板

**订阅消息模板（MVP 需要申请）：**
| 模板名称 | 适用角色 | 触发场景 |
|---------|---------|---------|
| 订单状态通知 | 买家 | 接单、发货、配送、签收、完成 |
| 新订单通知 | 供应商 | 买家下单付款 |
| 配送进度通知 | 买家 | 司机已接单、已取货、预计到达 |
| 新派单通知 | 司机 | 系统自动派单、抢单成功 |
| 结算到账通知 | 供应商/司机 | 订单结算、提现到账 |
| 审核结果通知 | 供应商/司机 | 入驻审核通过/驳回 |
| 售后通知 | 买家/供应商 | 售后申请、处理结果、平台裁决 |

**功能范围：**
- 订单状态通知：待接单、已接单、已发货、配送中、已送达、已完成
- 支付通知：支付成功、支付失败、退款到账
- 配送通知：司机已接单、司机已取货、预计X分钟送达
- 审核通知：供应商/司机入驻审核通过/驳回
- 售后通知：售后申请提交、供应商回复、平台裁决结果
- 通知渠道：微信订阅消息（优先）、站内信（兜底）
- 订阅管理：用户可在「消息设置」中管理已订阅的模板

### 5.8 运营后台（H5）

**功能范围：**

**工作台（首页）**

## 7. 核心数据模型（ER 概览）

```
User (用户)
  ├── 1:N → Address (地址)
  ├── 1:1 → Supplier (供应商扩展)
  │     └── 1:N → Product (商品)
  │           ├── 1:N → ProductSku (商品规格)
  │           └── 1:N → ProductReview (商品评价)
  └── 1:1 → Driver (司机扩展)

Category (品类)
  └── 1:N → Product (商品)

Order (订单)
  ├── 1:N → OrderItem (订单商品)
  ├── 1:1 → Payment (支付记录)
  ├── 1:1 → Delivery (配送任务)
  ├── 1:1 → Settlement (结算记录)
  └── 1:N → AfterSale (售后单)

Delivery (配送任务)
  └── N:1 → Driver (司机)
```

## 8. 非功能性需求

### 8.1 性能要求
- 页面首屏加载 < 2s（小程序）
- 商品搜索响应 < 500ms
- 下单接口响应 < 1s
- 支持 1000+ 并发用户（单城市MVP阶段）

### 8.2 安全要求
- 所有接口 HTTPS 传输
- 用户敏感数据（手机号、身份证、银行卡）加密存储
- SQL 注入、XSS、CSRF 防护
- 接口鉴权：JWT Token，不同角色权限隔离
- 支付接口签名校验、幂等性保证

### 8.3 可用性要求
- 服务可用性 99.5%+
- 数据库定时备份（每日全量 + 实时 binlog）
- 关键操作日志可追溯

### 8.4 兼容性
- 微信小程序：兼容微信 8.0+，主流 iOS/Android 机型
- H5 后台：兼容 Chrome、Safari、Edge 最新 2 个版本

## 9. 部署与运维方案

### 9.1 部署架构（MVP）

**自建后端，非微信云开发**——原因：业务逻辑复杂（派单、结算、仲裁），云开发云函数冷启动慢且成本不可控，自建更灵活。

```
                        ┌─────────────────┐
                        │   CDN（静态资源）│
                        │  小程序包 / H5   │
                        └────────┬────────┘
                                 │
┌────────────┐          ┌────────▼────────┐          ┌──────────────┐
│ 微信小程序  │  HTTPS   │   Nginx 反向代理  │  HTTPS  │  运营 H5 后台  │
│ 买家/供应商 │─────────▶│  (SSL 证书卸载)  │◀────────│  (静态页面)    │
│ /司机       │          └────────┬────────┘          └──────────────┘
└────────────┘                   │
                                   │ 反向代理
                          ┌────────▼────────┐
                          │  NestJS 后端服务  │
                          │  (PM2 多进程)     │
                          └────────┬────────┘
                                   │
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
              ┌──────────┐  ┌──────────┐  ┌──────────┐
              │  MySQL   │  │  Redis   │  │  OSS     │
              │ (主从)   │  │ (单机)   │  │ (对象存储)│
              └──────────┘  └──────────┘  └──────────┘
```

### 9.2 服务器配置（MVP 单城市阶段）

| 服务 | 配置建议 | 说明 |
|------|---------|------|
| 应用服务器 | 2核4G × 1台 | 跑 Nginx + NestJS + PM2，可承载 1000+ 并发 |
| 数据库 | 2核4G 云数据库 MySQL | 主从架构，自动备份 |
| Redis | 1核2G 云缓存 Redis | 缓存 + 派单队列 + 位置存储 |
| 对象存储 | 阿里云 OSS / 腾讯云 COS | 商品图片、资质、凭证 |
| CDN | 阿里云 CDN / 腾讯云 CDN | 加速 H5 后台和静态资源 |
| 域名 | 1个主域名 + 2个子域名 | api.xxx.com（后端）、admin.xxx.com（H5后台） |

### 9.3 HTTPS 与域名

- **必须 HTTPS**：微信小程序要求所有接口必须 HTTPS，且域名需要在小程序后台配置「request 合法域名」
- **SSL 证书**：使用 Let's Encrypt 免费证书或云厂商 DV 证书，自动续期
- **域名备案**：国内服务器必须 ICP 备案，小程序上线也要求备案

### 9.4 微信小程序配置

- **小程序类型**：企业主体小程序（个人主体无法开通微信支付）
- **微信支付**：需要开通「小程序 JSAPI 支付」和「商户转账到零钱/银行卡」功能
  - JSAPI 支付：买家付款到平台商户号
  - 商户转账：提现时打款给供应商/司机的微信零钱或银行卡
- **订阅消息**：在微信公众平台申请 7 个订阅消息模板（见 §5.7），获取模板 ID 后在运营后台配置
- **地理位置**：小程序后台配置「位置接口」权限，用于司机后台定位

### 9.5 对象存储（OSS/COS）

**图片上传流程：**
1. 前端请求后端获取上传签名（STS 临时凭证或预签名 URL）
2. 前端直传文件到 OSS（不走后端，节省带宽）
3. 上传成功后将文件 URL 返回给后端，后端存入数据库

**使用场景：**
- 商品主图/详情图
- 供应商/司机资质证件（营业执照、驾驶证等）
- 售后凭证图片
- 运营后台 Banner 图片

**安全控制：**
- 所有上传图片经过内容审核（OSS 自带或接入第三方）
- 敏感证件图片设置私有读写，通过签名 URL 访问
- 设置防盗链，防止图片被恶意引用

### 9.6 数据库备份与恢复

**备份策略：**
- **每日全量备份**：每天凌晨 3:00 自动执行全量备份，保留 30 天
- **实时 binlog 备份**：binlog 实时同步到对象存储，支持任意时间点恢复（PITR）
- **备份存储**：备份文件存储在对象存储（与数据库不同地域，防止同地域故障）

**恢复演练：**
- 每月至少进行一次恢复演练，确保备份可用
- 保留恢复操作文档

### 9.7 监控与告警

| 监控项 | 工具 | 告警阈值 |
|--------|------|---------|
| 服务器 CPU/内存/磁盘 | 云厂商监控 / Prometheus | CPU > 80%、内存 > 85%、磁盘 > 90% |
| 接口响应时间/错误率 | NestJS 日志 + APM（可选） | P95 > 3s、错误率 > 5% |
| 数据库连接数/慢查询 | MySQL 慢查询日志 + 监控 | 连接数 > 80%、慢查询 > 1s |
| Redis 内存/命中率 | Redis INFO + 监控 | 内存 > 80%、命中率 < 90% |
| 支付/转账异常 | 业务日志监控 | 支付成功率 < 99%、转账失败 |
| 派单积压 | 业务监控 | 未分配订单 > 10 个且超过 5 分钟 |

**告警渠道：** 企业微信/钉钉/飞书机器人 + 短信（严重告警）

### 9.8 CI/CD（建议）

MVP 阶段可以简化，但建议至少有：
- **代码仓库**：GitLab / GitHub / Gitee
- **自动化部署**：Git Push 到主分支后，通过 GitHub Actions / Jenkins 自动构建并部署到服务器
- **环境隔离**：至少有开发环境（dev）和生产环境（prod），数据库和 Redis 独立

### 9.9 安全加固

- **服务器**：关闭不必要端口、仅开放 22/80/443、使用密钥登录禁用密码、定期更新系统补丁
- **数据库**：禁止公网访问、仅允许应用服务器 IP 连接、使用最小权限账号
- **Redis**：设置密码、禁止公网访问（如需公网访问走 SSH 隧道）
- **接口安全**：已在 §8.2 列出（HTTPS、鉴权、签名、幂等）
- **敏感数据**：手机号、身份证、银行卡号加密存储（AES-256），日志中脱敏显示
